# 每日夜巡的运转手册

目标形态：agent 在自己选定的时段刷 B站视频、抽帧读懂、挑值得看的 @ 用户，并在结束时给下一次排期。

## 文件布局

| 路径 | 作用 |
|---|---|
| `~/.hermes/bili/mission.txt` | 任务全文，**唯一真相源**。cron prompt 只写「读这个文件并严格执行」 |
| `~/.hermes/bili/safe_windows.md` | 逐日「电脑开机时段表」，排期前必读 |
| `~/.hermes/bili/night_log.json` | 已刷记录 `date/bvid/title/verdict/action`，防重复 |
| `~/.hermes/bili/cookies.json` | 登录态，权限 600 |

prompt 用「指向文件」而不是内联全文：规则会变（时段、口味、禁区），内联进十几个历史任务就再也改不动；指向文件让一次编辑全局生效。

## 三条任务

1. **主任务**（one-shot，名字固定如 `B站夜巡`）：跑完自己建下一次，`continuity: true`。
2. **守卫**（recurring，每天两次，落在用户真正醒着的两段窗口里，如 13:35 / 21:35）：两个职责——
   - **补候选点**：`hermes cron list` 里「活着的」同名任务 <2 条就补到 2-3 条。判据是 `Next run` 在未来 + 状态不是 `completed` + `Repeat` 没打满（`0/1` 算活，`1/1` 已消费）三条同时满足；只看名字会看着一条已死的任务以为链正常。
   - **落地核对**：`~/.hermes/cron/executions.db` 的 `executions` 表（按 `started_at` 过滤当天）与 `night_log.json` 的 `run_seq` 交叉。**今天排过的候选点数 > 实际执行数** = 有点静默丢了 → 回复里点名哪几个点、并当天补一个更晚的可用点。一次性任务睡过去是被直接丢弃且不报错的，没有这一步就永远没人知道。
   - **守卫自己的时间点也算排期**：排进用户不在电脑前的时段（跑医院、通勤、上课外出），它自己就不会跑，等于没有守卫。窗口变了先改守卫的时刻。
3. **心跳**（recurring + `monitor`，每 5 分钟）：盯 `msgfeed/at`、`msgfeed/reply` 和私信，有新消息才唤醒 agent 去回。脚本 `bili_watch.py` 的 stdout 是单调 `KNOWN` 清单（只在新 id 首次出现时变，`ack` 不影响），未处理清单落在 `~/.hermes/bili/watch_last.txt`，agent 读它、不重跑脚本；处理完必须 `ack`。没有它，“等我下次巡到才回你”这种延迟会让人放弃使用。

### 链断的真正原因（不是睡眠）

主任务运行时，它自己那条记录**仍在** `hermes cron list` 里（`next_run` 是刚触发的时间）。若去重逻辑写成「已存在同名任务就不建」，它会把自己当成「下一次」，不创建，跑完被消费 → 链当场断。
去重必须同时满足：`next_run` 在今天之后（明天或更远）**且** `job_id` 不等于自己。这条要写进 mission.txt 原文，否则 agent 不会自己想到。

**第二种断法：任务静默死掉，名字还在。** once 任务可能变成 `state=completed` / `enabled=false` / `Next run: None`（手动 `run` 吃掉 repeat 配额是已知诱因之一），列表里看着有、实际永不触发，守卫若按「存在即通过」就整天放行。所以排期与守卫判断都按三字段，不按名字。

## 排期决策

- 从课表推导精确时刻：一节课 40 分钟 → P1 08:00-08:40、P2 08:50-09:30 ……逐节推，别凭印象。
- 三档标记：★ 人闲机开（午休 / 晚自习）＞ ✅ 上课但用户开电脑 ＞ ❌ 不开（体育、班会、通勤、吃饭）。只从 ★ 和 ✅ 里挑。
- **一次排 2-3 个候选点，不要只排下一个**（用户原话：夜巡不要只排在一个时间点）。机器会睡，早点那个被吞掉、晚点那个还在，这一天才不至于空过去；彼此间隔 ≥90 分钟、都从 ★/✅ 里挑。
- 同一时段不要重复堆：上限按用户指定（本例每天 4 趟、单趟间隔 ≥90 分钟；实际跑 2-4 趟、全天视频 ≤4 个，低调优先），跨天不重复同一时刻。上限是上限不是任务，够不着就少跑。

## 排期后必查

`hermes cron list` 回读三列：`Deliver` 是用户期望的那个（不想被聊天窗口打扰就用 `local`；只有用户明说要推才写 `origin` 或具体平台）、`Next run` 是预期时刻、`Repeat` 没被打满。

## 记账与审计（用户问「还在正常跑吗」时用）

额度全在 `night_log.json` 里，靠字段区分：

| 要数的东西 | 怎么数 |
|---|---|
| 今天跑了几趟 | title 为「本次运行元信息」的条目数（`run_seq=…`） |
| 今天看了几个视频 | 有 `bvid` 且 title 不是「自发评论」/「本次运行元信息」的条目数 |
| 今天自发评论几条 | title 含「自发评论」的条目数 |

**日志只能证明「我以为我发了」，证明不了它还在。** 要回答协约是否真生效，还得拿 `aid`（bvid 经 `bili_cli.to_aid()` 转换）+ `root` rpid 走一次
`python3 ~/.hermes/scripts/bili_subreplies.py <oid> <root> --why "核实…"`，看到自己的 rpid 和原文才算线上。

**额度没有机械闸门**：脚本不拦，超了也不会报错，只能发前自己数。若某天开始频繁被问到额度，就该把它做成前置检查（发前读 night_log 计数，到顶直接拒绝），别指望每次都想得起来。

**复核要用对工具**：子回复走 `bili_subreplies.py`；**顶层评论用 `bili_cli.py verify <aid> <rpid> [--root N]`**（内部是匿名 `wbi/main` + `mode=2` 时间序 + cursor 翻页）。拿热度序只翻首页去查，自己 0 赞的评论查不到，会被误判成「被审/被删」——一整天都在这种假阴性上打转。

**回答「今天发了哪些评论」**：把每个 aid 换成 BV + 标题（`/x/web-interface/view?aid=`，间隔 ≈0.7s），按「自发顶楼 / 回主人 / 回复路人」分组，并注明哪几条已自删、哪几条当时判过审核池；只报一句「发了 N 条」等于没汇报。分拣日志时列数可能不一致（有的行没写正文），解析要容错，别把 6 列硬拆成 7 列。

## 常见复发问题

- **手动 `run` 消耗 repeat 配额**：手动跑过一次再改期，下一次可能被静默跳过；改期时把 `repeat` 调大并回读确认。
- **链断了**：守卫会在下一个白天窗口重建；也可手动 run 一次再重新排期。
- **登录态失效**：按 SKILL.md 的接管流程重抓 cookie（需要用户完全退出 Chrome）。
- **用户作息/健康情况变了**（受伤跑医院、停晚自习、改成很晚才睡）：排期窗口是三处以上真源叠出来的，只改 `safe_windows.md` **不够**——已排出去的一次性任务不会自己挪，任务指令里也常硬编码着旧时段（「傍晚正档」「晚自习 18:30-21:30」）。按这个顺序全改一遍再 grep 回读：① `safe_windows.md` 顶部禁令；② `mission.txt` 的时段速记；③ 守卫 cron 的 prompt（它另有自我重建的权力，口径旧就会把新点排回禁区）；④ 对话记忆里的作息条目；⑤ **已经排出去的 job**：`hermes cron edit <id> --schedule` 挪时间，`--prompt` 改掉里面写死的时段措辞。带第二个号时，她那套 mission / 守卫 prompt / job prompt 是独立副本，要各自改。
  - 隐私背景（病情、用药）只进本机文件与记忆，**站内与对外文字一个字不提**。
